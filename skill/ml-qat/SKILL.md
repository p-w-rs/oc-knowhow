# Quantization-aware training

Ground truth: Jacob et al. 1712.05877 (integer-only inference, QAT with folded BN), Nagel et al. *A White Paper on
Neural Network Quantization* 2106.08295 (the best practical overview), Wu et al. NVIDIA 2004.09602 (INT8 recipe),
Esser et al. LSQ 1902.08153, Bengio et al. STE 1308.3432. Cite through `library_search`. For deploying the result with
TensorRT see the ml-deploy skill.

## 1. PTQ first, QAT when it is not enough

1. Measure the **float baseline** on the real evaluation set and the target metric.
2. **PTQ** (post-training quantization) with good calibration: 128–512 representative samples (ModelOpt
   recommends this range), per-channel weights, a calibration method that clips outliers (percentile/entropy/MSE for
   INT8 activations; AWQ/GPTQ (2210.17323)/SmoothQuant for LLM weights).
3. Mixed precision before QAT: find sensitive layers (quantize one layer at a time and measure; ModelOpt
   `auto_quantize` searches per-layer formats under an effective-bits budget) and keep them in higher precision —
   typically the first and last layers, attention softmax/LayerNorm, and layers with large outliers.
4. **QAT** when PTQ still loses more than the accepted margin, or for aggressive targets (INT4 weights + INT8
   activations, ≤ 4-bit, small models, regression/detection heads that are sensitive).

## 2. How QAT works

- **Fake quantization**: in the forward pass weights/activations are quantized and immediately dequantized
  (`x̂ = s·clamp(round(x/s) + z, qmin, qmax) − s·z`), so the network trains against the rounding and clipping error
  while computing in float.
- **Straight-through estimator** (STE): treat `round` as identity in the backward pass; gradients are zeroed outside
  the clipping range.
- **Scales**: from running min/max or percentiles (observers), or **learned** (LSQ 1902.08153: scale is a parameter
  with a scaled gradient; LSQ+ 2004.09576 adds learned offsets and better init). Learned scales matter most below
  8 bits; initialize them from a PTQ calibration, not at random.
- **Granularity**: per-tensor activations (INT8) or per-token (LLMs); per-output-channel weights for convs/linears;
  per-group (32–128) for INT4 weights; block scales for FP4 (NVFP4: 16-element blocks, FP8 E4M3 scale + FP32 tensor scale; OCP MXFP4: 32-element
  blocks, power-of-two E8M0 scale).
- Symmetric for weights; asymmetric (zero point) for activations after ReLU-like functions if the backend supports it.
- Formats: INT8 (everywhere), FP8 E4M3 (Hopper/Ada/Blackwell, Thor; often PTQ is enough), INT4 weight-only (LLMs),
  NVFP4 (Blackwell/Thor).

## 3. Recipe for vision/CNN/ViT models (INT8, INT4 weights)

1. Start from the **fully trained float model** (QAT from scratch is slower and rarely better).
2. Fold BatchNorm into convs as the deployment backend will (Jacob et al.: simulate the folded weights during QAT, or
   freeze BN statistics after a few epochs).
3. Calibrate once (PTQ) to initialize scales, then fine-tune with fake quantization.
4. Train **~10% of the original epochs** (ModelOpt's guidance; LLMs often < 1% of pretraining) with the LR at about
   **1–10% of the original peak**, cosine or linear decay to zero, same augmentation, no strong extra regularization.
5. **Freeze observers / activation ranges** after the first part of QAT and **freeze BN statistics** near the end so
   the last epochs fine-tune against fixed quantization.
6. Distillation helps: use the float model as teacher (KL on logits, or features) — **QAD** in ModelOpt.
7. Evaluate the **converted / exported** model (real INT8 engine), not the fake-quant PyTorch model; differences point
   to mismatched quantizer placement, fusion, or rounding between training and the backend.

## 4. LLMs

- Weight-only INT4/INT3 with group scales is usually PTQ (AWQ, GPTQ); QAT when going lower or quantizing activations
  and the KV cache.
- **LLM-QAT** (2305.17888): data-free QAT using data generated by the model itself, KV-cache quantization.
- **EfficientQAT** (2407.11062): block-wise training of all parameters, then end-to-end training of quantization
  parameters; cheaper than full QAT.
- **ParetoQ** (2502.02631): compares 1-, 1.58-, 2-, 3- and 4-bit QAT under one framework; a transition between 2
  and 3 bits: at ≥ 3 bits the QAT model stays close to the pretrained one, at ≤ 2 bits representations change
  drastically (needs a longer QAT budget); ternary/2/3-bit were on the size–accuracy frontier ahead of 4-bit.
- Use the PTQ result as the starting point; small learning rates; evaluate on downstream tasks, not only perplexity.

## 5. Tools

**torchao** (PyTorch-native; CPU/edge/LLM backends):

```python
import torch
from torchao.quantization import quantize_, Int8DynamicActivationIntxWeightConfig, PerGroup
from torchao.quantization.qat import QATConfig

base = Int8DynamicActivationIntxWeightConfig(weight_dtype=torch.int4, weight_granularity=PerGroup(32))
quantize_(model, QATConfig(base, step="prepare"))   # nn.Linear -> FakeQuantizedLinear
train(model)                                        # usual loop, lower LR
quantize_(model, QATConfig(base, step="convert"))   # real quantized model
```

Tested with torchao 0.17 (CPU). The older name `Int8DynamicActivationInt4WeightConfig` is **not** exported in recent
torchao (0.14, 0.17, 0.18): use the Intx config above. Other base configs QAT accepts (docs): `Int4WeightOnlyConfig`
(the docs' main example, `group_size=32`), `IntxWeightOnlyConfig`, `Float8DynamicActivationFloat8WeightConfig`,
`Float8DynamicActivationInt4WeightConfig`, NVFP4/MX configs. Custom schemes:
`QATConfig(activation_config=IntxFakeQuantizeConfig(torch.int8, "per_token", is_symmetric=False),
weight_config=IntxFakeQuantizeConfig(torch.int4, group_size=32), step="prepare")`; `Float8FakeQuantizeConfig` for
FP8. **Only `nn.Linear` and `nn.Embedding` are swapped; convs are left in float.** For CNNs in the PyTorch stack use
PT2E export QAT: `torch.export.export(model, args).module()` → `prepare_qat_pt2e(m, quantizer)` → train →
`convert_pt2e(m)` (import from `torchao.quantization.pt2e.quantize_pt2e`; the old `torch.ao.quantization` path is
gone in recent PyTorch); the backend's `Quantizer` (e.g. XNNPACK / ExecuTorch, x86 Inductor) decides placement and
conv+BN folding; use `move_exported_model_to_train/eval` instead of `model.train()/eval()`.

**NVIDIA ModelOpt** (for TensorRT / TensorRT-LLM; convs and linears):

```python
import modelopt.torch.quantization as mtq
model = mtq.quantize(model, mtq.INT8_DEFAULT_CFG, forward_loop)   # inserts quantizers + calibrates (PTQ)
mtq.print_quant_summary(model)
train(model, ...)                                                  # QAT: fine-tune; quantizer states typically frozen
torch.onnx.export(model, sample, "model_qat.onnx")                # Q/DQ nodes → TensorRT (strongly typed, see ml-deploy)
```

Save/restore quantizer state with `mto.save` / `mto.restore`. `mtq.fold_weight` only speeds up fake-quant evaluation;
after it the model can no longer be exported to ONNX or trained with QAT (ModelOpt docs).

## 6. Pitfalls

- QAT with a high LR or long schedule destroys the float model's accuracy; it is a fine-tune.
- Quantizer placement in training must match the deployed graph (fused conv+BN+ReLU, residual adds, concat scales);
  mismatches show up as accuracy loss only after export.
- Activation outliers (transformers): per-token or SmoothQuant-style scaling, or keep that layer in FP16/FP8.
- Compare at equal evaluation settings and several seeds; report float, PTQ, QAT and deployed-engine accuracy plus
  latency together (experiment-design skill).
